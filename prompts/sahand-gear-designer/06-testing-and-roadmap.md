# ✅ 06 — آزمون، معیار پذیرش و نقشهٔ اجرا

## 1. ترتیب پیشنهادی توسعه

هر مرحله باید به build قابل اجرا و آزمون‌های سبز ختم شود. ابتدا هستهٔ کوچک اما واقعی بساز؛ تا وقتی جریان انتها‌به‌انتها وجود ندارد، ده‌ها گزینهٔ نمایشی اضافه نکن.

| مرحله | خروجی | شرط عبور |
|---|---|---|
| 0 — بررسی و طراحی | گزارش مخزن، معماری، محدودیت هستهٔ CAD/مش، وابستگی‌ها و برنامه | تصمیم‌های فنی، مجوزها و ریسک‌ها ثبت شده باشند |
| 1 — اسکلت ویندوزی | راهکار، WPF/MVVM یا فناوری انتخابی، فارسی/RTL، وزیرمتن محلی، صفحهٔ آغاز | build اجرا شود؛ اینترنت و نصب فونت لازم نباشد |
| 2 — برش عمودی | چرخ‌دندهٔ خارجی ساده، فرم پارامتر، هندسهٔ سه‌بعدی، نمای تعاملی | چند پارامتر معتبر/نامعتبر آزموده شوند؛ خطا UI را نشکند |
| 3 — پروژه و خروجی | ذخیره/بازگشایی بومی و حداقل یک فرمت mesh عملیاتی | round-trip و parser/اعتبارسنجیِ فایل موفق باشد |
| 4 — خانواده‌های پایه | داخلی، مارپیچ، رک و ویژگی‌های بدنه به ترتیب اولویت | هر نوع آزمون مستقل و محدودیت مستند داشته باشد |
| 5 — مونتاژ | جفت‌دنده، قطار چندمرحله‌ای، سیاره‌ای پایه | هندسه، فاز، قیود و نسبت‌های نمونه آزموده شوند |
| 6 — CAD/کیفیت | مبدل‌های بیشتر، B-rep در صورت امکان، presetهای mesh | ماتریس capability و آزمونِ format به‌روز باشد |
| 7 — گزارش و انتشار | رضایت، صف آفلاین، API اختیاری، installer/portable | حالت قطع شبکه و عدم‌ارسالِ بدون رضایت آزموده شود |

اگر زمان یا امکانات ابزار محدود است، مرحلهٔ بعدی را کوتاه کن؛ مرحلهٔ انجام‌نشده را به‌عنوان قابلیت کامل اعلام نکن.

## 2. آزمون‌های واحد هندسه و پارامتر

### آزمون‌های مشترک

- مقدار صفر، منفی، `NaN`, `Infinity`، مقدار بسیار بزرگ و حداقل/حداکثر عملی برای همهٔ پارامترهای عددی.
- اعشار، تبدیل mm/inch و تبدیل رفت‌وبرگشت بدون تغییر اندازهٔ واقعی.
- تعداد دندانهٔ نامعتبر، ورودی غیرعددی، حذف/بازگردانی، دقت محاسبات و گردکردن فقط در UI.
- تکرار ساخت مدل با ورودی برابر، خروجی پایدار و قابل مقایسه باشد.
- خطای هندسی نتیجهٔ نیمه‌کاره/mesh خراب را به‌عنوان قطعهٔ معتبر ذخیره نکند.
- property-based/fuzz test برای پارامترهای تصادفیِ مجاز؛ crash یا تولید مختصات غیرمحدود ممنوع.

### نمونه‌های هندسی

برای هر خانوادهٔ «پیاده‌سازی‌شده» حداقل این موارد ثبت شود:

1. چند ورودی متعارف که هندسهٔ معتبر می‌سازند.
2. ورودی مرزی (کمترین دندانه، زاویهٔ نزدیک حد، پهنای کوچک) همراه با نتیجهٔ مورد انتظار یا هشدار.
3. مورد نامعتبر که باید با پیام روشن رد شود.
4. تعداد نقاط/مثلث یا حدودِ bounding box، محور و تقارن برای جلوگیری از برگشت خطا.
5. مقایسه با محاسبهٔ مستقل/مرجع معتبر؛ tolerance عددی در تست و دلیل آن ثبت شود.

### جفت‌ها و مونتاژ

- جفت سادهٔ خارجی: فاصلهٔ مرکز/نسبت/جهت دوران در حالت مرجع درست باشد.
- جفت داخلی: فاصلهٔ مرکز، جهت مش و برخورد دندانه با رینگ بررسی شود.
- جفت مارپیچ: سمت/جهت و سازگاری زاویه کنترل شود.
- رک و پینیون: حرکت انتقالی با گام دندانه سازگار باشد.
- قطار مرکب: نسبت کل و محور مشترک با نمونهٔ دستی تطبیق داده شود.
- سیاره‌ای: قید هندسی، موقعیت مساوی سیاره‌ها، امکان فازشدن و رابطهٔ سرعتِ عضوهای نمونه آزموده شود؛ حالت ناسازگار رد/هشدار شود.
- اگر برخورد هندسی فقط با تقریب/مش بررسی می‌شود، آزمون و UI باید «تقریبی» بودن آن را اعلام کنند.

## 3. آزمون رابط کاربری و RTL

- شروع تازه روی Windows بدون فونت نصب‌شده: Vazirmatn همراه برنامه بارگذاری و متن فارسی درست شکل‌دهی شود.
- راست‌به‌چپ در صفحهٔ آغاز، dialogها، درخت مونتاژ، فرم‌ها، منوها، هشدار و گزارش.
- متن ترکیبی فارسی/انگلیسی، `z1/z2`، کسر، علامت منفی، اعشار، درجه، mm/inch و مسیرهای `C:\...` خوانا و جهت‌گیری درست داشته باشند.
- کنترل با ماوس و صفحه‌کلید، ترتیب Tab، فوکوس قابل‌دیدن، Enter/Escape و Undo/Redo.
- نمایشگر 100/125/150/200% DPI، resize پنجره، حالت روشن/تیره، پنجرهٔ بازخورد و خروجی.
- ورودیِ نامعتبر باید متن/آیکون/تمرکز فیلد درست داشته باشد؛ فقط رنگ قرمز کافی نیست.
- فایل/پروژه با نام فارسی و مسیر دارای فاصله ذخیره/بازگشایی شود.

## 4. آزمون ذخیره، بازیابی و خروجی

| موضوع | سناریوی آزمون |
|---|---|
| پروژهٔ بومی | ساخت چند قطعه، ذخیره، بستن/بازگشایی و مقایسهٔ پارامتر/ساختار/جهت |
| نسخهٔ schema | بازکردن فایل قدیمی، مهاجرت قابل بازگشت/پشتیبان و نگهداری فیلد ناشناخته |
| ذخیرهٔ اتمی | قطع/شبیه‌سازی خطا حین ذخیره؛ نسخهٔ قبلی سالم بماند |
| STL | باینری/متنی (اگر هر دو پیاده شده)، بررسی header، اندازه و واحد همراه |
| OBJ/MTL | ترتیب فایل‌ها، مسیر نسبی مواد، محور و مش؛ نبود MTL رفتار روشن داشته باشد |
| GLB/glTF | ساختار glTF، تبدیل meter، صحنه و قطعات؛ آزمون parser/round-trip |
| 3MF/PLY/AMF | فقط در صورت پیاده‌سازی؛ ساختار استاندارد و متادیتای ادعاشده بررسی شود |
| STEP/IGES | فقط با هستهٔ B-rep؛ فایل به‌عنوان جامد/سطح واقعی validate و در parser سازگار باز شود |
| مسیر و نام فایل | فارسی، فاصله، نویسهٔ غیرمجاز، عدم دسترسی، دیسک پر و فایلِ از قبل موجود |
| کیفیت مش | presetها، تلرانس، حد مثلث، نرمال، رأس‌های تکراری، زمان و مصرف حافظه |
| شکست صادرکننده | فایل ناقص به‌عنوان موفق باقی نماند؛ پیام قابل فهم و log محلی ثبت شود |

حداقل یک مدل نمونه برای هر فرمتِ واقعاً پشتیبانی‌شده نگه‌دار و در راهنما توضیح بده با چه برنامه/ابزاری اعتبارسنجی شده است. از ادعای «در همهٔ نرم‌افزارها باز می‌شود» پرهیز کن؛ نسخه و نوع فرمت را بیان کن.

## 5. آزمون آفلاین، حریم خصوصی و ارسال

- نصب تازه روی ماشین/VM یا محیط با شبکهٔ قطع‌شده: برنامه آغاز و قابلیت‌های هسته اجرا شوند.
- مانیتور شبکه/لاگ تست نشان دهد هنگام راه‌اندازی معمول هیچ request اجباری برای فونت، لایسنس، update یا telemetry نیست.
- ارسال گزارش خاموش: هیچ داده‌ای به شبکه ارسال نشود؛ خطا فقط محلی ثبت شود.
- رضایت روشن: preview گزارش و انتخاب کاربر رعایت شود؛ مسیر/محتوای پروژه حذف یا پوشیده باشد.
- آفلاین با رضایت: صف محلی و وضعیت «در انتظار»؛ بعد از اتصال فقط در صورت policy/اجازهٔ معتبر ارسال شود.
- endpoint نامعتبر، timeout، TLS error، پاسخ سرور خطادار و تکرار ارسال؛ پروژه و صف امن بمانند و ارسال دوباره ناخواسته نشود.
- endpoint/server تنظیم‌نشده: برنامه به‌وضوح بگوید ارسال واقعی در دسترس نیست.
- بررسی مخزن و binary برای رمز SMTP، API secret، کارت کامل، token، dump یا دادهٔ نمونهٔ خصوصی.
- کاربر بتواند رضایت را لغو و گزارش‌ها/صف محلی را حذف کند.

## 6. معیار پذیرش نسخهٔ قابل‌تحویل

نسخه فقط در صورتی «قابل‌تحویل» نامیده شود که همهٔ موارد مرتبطِ زیر نتیجهٔ مستند داشته باشند:

### عملکرد

- [ ] یک پروژهٔ تازه ساخته، ذخیره، بسته و دوباره باز می‌شود.
- [ ] حداقل یک نوع چرخ‌دندهٔ پارامتریک از ورودی تا نمایش سه‌بعدی اجرا می‌شود.
- [ ] ورودی نامعتبر با پیام قابل‌فهم متوقف می‌شود و UI نمی‌ریزد.
- [ ] جفت/مونتاژهای اعلام‌شده واقعاً دارای پارامتر و رابطهٔ قابل بازتولید هستند.
- [ ] دست‌کم یک فرمت خروجیِ اعلام‌شده، فایل معتبر ایجاد می‌کند و پس از نوشتن بررسی می‌شود.
- [ ] واحد، محور، کیفیت و محدودیت قالب در UI/گزارش مشخص‌اند.

### زبان و آفلاین

- [ ] فارسی و RTL در همهٔ صفحه‌های اصلی آزموده شده‌اند.
- [ ] وزیرمتن از منابع بسته‌بندی‌شده بارگذاری می‌شود؛ نصب جدا لازم نیست.
- [ ] هسته بدون اینترنت کار می‌کند؛ نصب/اجرا asset اینترنتی نمی‌خواهد.
- [ ] هیچ ارسال/تحلیلی بدون رضایت روشن انجام نمی‌شود.

### مهندسی و تحویل

- [ ] تست‌های واحد اصلی سبز هستند و نتایج build/test واقعی گزارش شده‌اند.
- [ ] وابستگی‌ها و مجوزها مستند هستند.
- [ ] فایل راهنمای کاربر و راهنمای توسعه/ساخت موجود است.
- [ ] وضعیت انواع و فرمت‌ها (پیاده‌شده/محدود/برنامه‌ریزی‌شده) قابل مشاهده است.
- [ ] اشکال‌های شناخته‌شده و موارد خارج از محدوده فهرست شده‌اند.

## 7. قالب گزارش نهاییِ هوش مصنوعی

در پایان، پاسخ را با این بخش‌ها جمع‌بندی کن:

1. **چه ساخته شد؟** — قابلیت‌های واقعاً اجراشده، با تفکیک UI/هندسه/خروجی.
2. **چه چیزی پشتیبانی نمی‌شود یا آزمایشی است؟** — خانواده‌ها، فرمت‌ها، استانداردها و تحلیل‌ها.
3. **چطور اجرا/ساخته/آزمون می‌شود؟** — فرمان‌ها و نسخهٔ ابزار لازم، بدون فرضِ انجام آزمونی که اجرا نشده.
4. **فایل نهایی کجاست؟** — راهکار، artifact ویندوزی، نمونه‌ها و مستندات.
5. **وضعیت آفلاین/گزارش:** چه چیزی محلی است، آیا backend واقعاً نصب شده، و ارسال در چه وضعیتی است.
6. **محدودیت‌ها و گام بعدی:** کوتاه، مشخص، بدون وعدهٔ نامحدود.

## 8. آزمون افزوده‌های پیشنهادی

این آزمون‌ها فقط زمانی معیار پذیرش می‌شوند که قابلیت متناظر پیاده‌سازی شده باشد؛ قابلیت ناتمام باید در UI/نقشهٔ راه صریحاً غیرفعال یا مرحلهٔ بعدی علامت بخورد.

| قابلیت افزوده | آزمون پذیرش |
|---|---|
| Autosave و بازیابی | شبیه‌سازی بسته‌شدن غیرمنتظره؛ بازیابی آخرین نسخهٔ سالم، عدم خراب‌شدن فایل قبلی و امکان رد/پاک‌کردن نسخهٔ recovery |
| دستیار اندازه/نسبت | برای چند مسئلهٔ مرجع، همهٔ پیشنهادها در محدوده باشند؛ محاسبهٔ نسبت/ابعاد دوباره تأیید شود؛ نبود جواب و محدودیت‌ها صادقانه گزارش شوند |
| بررسی برخورد/فاصله | قطعهٔ برخوردکننده، قطعهٔ دارای فاصله و حالت مرزی؛ نوع الگوریتم و false-positive/false-negative در تست ثبت شود |
| اندازه‌گیری/مقطع | اندازهٔ شناخته‌شده در چند واحد و جهت محور؛ صفحهٔ مقطع مدل را تغییر ندهد و نتیجه tolerance/واحد درست داشته باشد |
| نقشهٔ دوبعدی | مقیاس، نما، جهت، خط مرکز، ابعاد، فارسی/لاتین، فونت و چاپ PDF/DXF با نمونهٔ مرجع کنترل شود |
| سینماتیک | جهت/نسبت نمونه‌های جفت، قطار و سیاره‌ای با محاسبهٔ مستقل تطبیق؛ عضو ثابت و وضعیت حل‌نشده در UI آشکار باشد |
| Variant/مقایسه | نسخهٔ پایه دست‌نخورده، تفاوت پارامتر/هشدار درست و بازگشت/ذخیره پایدار باشد |
| Batch export | هر خروجی به ورودی‌اش قابل ردیابی؛ توقف/شکست یک مورد، گزارش موردهای دیگر را از بین نبرد |
| واردکردن مرجع | فایل‌های خراب/بزرگ و format mismatch به‌صورت کنترل‌شده رد شوند؛ مش ورودی خودکار به مدل پارامتریکِ معتبر تبدیل نشود |
| تحلیل استحکام | محاسبه با مثال مرجع و واحدها اعتبارسنجی؛ استاندارد/نسخه/فرض‌ها چاپ شود؛ خارج از دامنه به‌عنوان عدم‌تأیید گزارش شود |
