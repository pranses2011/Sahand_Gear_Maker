# 📋 چک‌لیست انتشار و نگهداشت مخزن

> **قاعدهٔ طلایی:** با هر تغییر معنادار در برنامه، سه چیز باید همگام با کد به‌روز شوند:
> **README**، **«دربارهٔ» (About) مخزن** و **شمارهٔ نسخه + اسکرین‌شات‌ها**.
> مخزنی که مستنداتش از کد عقب باشد، مخزنی نیست که کاربر بتواند به آن اعتماد کند.

---

## ۱) شمارهٔ نسخه — منبع واحد

- نسخه **فقط** در `$(Version)` فایل‌های `.csproj` تعریف می‌شود (نباید جای دیگری دستی نوشته شود).
- خواندن نسخه در زمان اجرا فقط از `AppInfo.Version` (خواندن از فرادادهٔ اسمبلی MSBuild).
- نمایش نسخه در این مکان‌ها باید همیشه برقرار باشد:
  - عنوان پنجرهٔ اصلی: «طراح چرخ‌دنده سهند — Sahand Gear Designer v{نسخه}»
  - سربرگ برنامه (زیرنویس انگلیسی)
  - صفحهٔ «درباره»
- قالب تگ انتشار: `vX.Y.Z` (مثلاً `v0.3.0`).

## ۲) اسکرین‌شات‌ها — همیشه واقعی و به‌روز

- منبع تصاویر **فقط خروجی خود برنامه** است؛ هیچ تصویر طراحی‌شدهٔ دستی جایگزین نمی‌شود.
- دو مولد:
  1. **رندرهای موتور** (خانواده‌ها + صحنه‌ها): ابزار `src/SahandGearMaker.Screenshots`
  2. **کپچر رابط کاربری**: خود برنامهٔ واقعی با پرچم `--screenshot <پوشه>`
     (⚠️ کپچر UI هرگز از میزبان بیرونی انجام نمی‌شود؛ بارگذاری منابع WPF در اسمبلی
     دیگری خطای `DeferredBinaryDeserializerExtension` می‌دهد.)
- CI ویندوزی (`windows.yml`) بعد از هر پوش به `main` همهٔ تصاویر را بازتولید و به
  `docs/screenshots/` کامیت می‌کند (`[skip ci]`).
- **هر تصویر جدید باید همان روز به گالری README اضافه شود** — گالری باید همیشه
  «فهرست کامل» فایل‌های موجود در `docs/screenshots/` باشد.

## ۳) README — بازنویسی با هر تغییر

با هر merge به main که رفتار/ظاهر/قابلیت را تغییر می‌دهد:

- [ ] بخش «تازه‌ها / نقشهٔ راه» با تغییرات جدید به‌روز شود.
- [ ] جدول قابلیت‌ها و گالری کامل بازبینی شود (تصاویر حذف/اضافه‌شده).
- [ ] شمارهٔ نسخه در عنوان، بج‌ها و پیوند‌های دانلود مطابق تگ جدید شود.
- [ ] پیوند بستهٔ پرتابل به تگ درست Releases اشاره کند.

## ۴) «دربارهٔ» (About) مخزن — همگام با README

با همان ضربان README، توضیحات و تاپیک‌های مخزن از طریق API به‌روز شوند:

```bash
curl -X PATCH https://api.github.com/repos/pranses2011/Sahand_Gear_Maker \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"description": "<توضیح جدید یک‌پاراچهٔ فارسی + انگلیسی>"}'
```

- توضیح باید قابلیت‌های شاخص فعلی + «کاملاً آفلاین/فارسی/RTL» را در بر گیرد.
- تاپیک‌ها فقط با افزودن قابلیت‌های جدید تغییر کنند (نه با هر بازنویسی).

## ۵) فرایند انتشار (تگ → Release خودکار)

1. اطمینان از سبز بودن هر سه ورک‌فلو روی `main`.
2. در صورت تغییر API/رفتار، به‌روزرسانی `docs/USER-GUIDE.md` و `docs/BUILD.md`.
3. تعیین نسخهٔ جدید در `.csproj` (اگر تغییر فقط اصلاح انتشار است، همان نسخه نگه داشته
   می‌شود و فقط تگ جابه‌جا می‌شود، مشروط بر آنکه هیچ Release موفقی از آن نسخه منتشر نشده باشد).
4. ساخت تگ: `git tag vX.Y.Z && git push origin vX.Y.Z`
5. ورک‌فلو `release-windows` به‌صورت خودکار: بیلد + آزمون → انتشار پرتابل self-contained →
   ساخت Release با هر دو ZIP و یادداشت‌های تغییر خودکار.
6. تأیید نهایی: وجود هر دو asset در صفحهٔ Releases.
