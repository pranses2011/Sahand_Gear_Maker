# 🏗️ معماری و تصمیم‌های فنی — Sahand Gear Designer

این سند خروجی «مرحلهٔ ۰ — بررسی و طراحی» از [نقشهٔ اجرا](../prompts/sahand-gear-designer/06-testing-and-roadmap.md) است: معماری انتخاب‌شده، تصمیم‌های فنی، محدودیت‌ها و ریسک‌ها قبل از پیاده‌سازی ثبت می‌شوند.

## ۱. وضعیت مخزن و ورودی کار

مخزن در شروع کار فقط شامل بستهٔ پرامپت (پوشهٔ `prompts/sahand-gear-designer`)، `LICENSE` (MIT) و `README.md` بود؛ هیچ کد، فناوری تثبیت‌شده یا وابستگی‌ای وجود نداشت. بنابراین طبق [پرامپت اصلی](../prompts/sahand-gear-designer/01-master-prompt.md) فناوری مبنا **C# / .NET LTS + WPF با الگوی MVVM** انتخاب شد.

## ۲. پشتهٔ فناوری و نسخه‌ها

| لایه | فناوری | نسخه | دلیل |
|---|---|---|---|
| Runtime | .NET | 8.0 (LTS، پشتیبانی‌شده تا نوامبر ۲۰۲۶) | الزام پرامپت: نسخهٔ پشتیبانی‌شدهٔ LTS |
| زبان | C# | 12 (همراه SDK 8.0) | — |
| UI | WPF + MVVM | net8.0-windows | الزام پرامپت برای پوستهٔ ویندوزی |
| MVVM | CommunityToolkit.Mvvm | 8.x | MIT، بدون وابستگی native، نگهداری‌شده توسط تیم .NET |
| آزمون | xUnit | 2.x | استاندارد اکوسیستم .NET |
| سریال‌سازی | System.Text.Json | داخل SDK | بدون وابستگی بیرونی، آفلاین |

**سیاست وابستگی:** حداقل وابستگی ممکن؛ همهٔ مجوزها MIT؛ هیچ کتابخانهٔ native، سرویس ابری یا مولفهٔ نیازمند اینترنت در هسته وجود ندارد. رندر سه‌بعدی پیش‌نمایش با یک رندرر نرم‌افزاری سبک (رستر‌ساز + Z-Buffer روی `WriteableBitmap`) داخل خود برنامه پیاده می‌شود تا از وابستگی به موتور گرافیکی بیرونی (OpenTK/SharpDX/HelixToolkit) که همگی native یا سنگین‌اند پرهیز شود؛ نتیجه: بستهٔ portable سبک و کاملاً آفلاین. محدودیت این تصمیم در بخش «محدودیت‌ها» ثبت شده است.

## ۳. مرزهای معماری (طبق پرامپت اصلی)

```text
SahandGearMaker.sln
├─ src/
│  ├─ SahandGearMaker.Domain/        → net8.0  (قابل آزمون روی لینوکس)
│  │    مدل پروژه، انواع چرخ‌دنده، پارامترها، واحدها، کاتالوگ قابلیت، کدهای اعتبارسنجی
│  ├─ SahandGearMaker.Geometry/      → net8.0  (قابل آزمون روی لینوکس)
│  │    موتور اینولوت، پروفیل، ساخت بدنهٔ سه‌بعدی و مش، ویژگی‌های بدنه
│  ├─ SahandGearMaker.Assembly/      → net8.0  (قابل آزمون روی لینوکس)
│  │    جفت‌دنده، روابط مونتاژ، فاصلهٔ محور، قیود قطار و سیاره‌ای (ویلیس)
│  ├─ SahandGearMaker.Persistence/    → net8.0  (قابل آزمون روی لینوکس)
│  │    پروژهٔ بومی .sgdproj، ذخیرهٔ اتمی، مهاجرت نسخهٔ schema
│  ├─ SahandGearMaker.Exports/       → net8.0  (قابل آزمون روی لینوکس)
│  │    مبدل‌های مش STL/OBJ/PLY/GLB، تنظیم کیفیت، اعتبارسنجی پس از نوشتن
│  ├─ SahandGearMaker.Math/          → net8.0  (قابل آزمون روی لینوکس)
│  │    جبر خطی سبک: بردار، ماتریس، مثلث، ابزار مش
│  └─ SahandGearMaker.App/           → net8.0-windows  (فقط ساخت روی ویندوز)
│       پوستهٔ WPF/MVVM فارسی RTL، فونت وزیرمتن محلی، رندرر پیش‌نمایش،
│       صفحهٔ آغاز/طراح/خروجی/درباره/بازخورد، تنظیمات، صف محلی
├─ tests/
│  └─ SahandGearMaker.Tests/         → net8.0 (اجرا روی لینوکس؛ xUnit)
├─ samples/                          → پروژه‌های نمونهٔ بی‌خطر .sgdproj
├─ docs/                             → مستندات کاربر/توسعه/ماتریس قابلیت
└─ .github/workflows/                → CI: build+test هسته روی ubuntu-latest
```

قواعد وابستگی یک‌طرفه: `App → همه` ، `Exports/Assembly/Persistence → Domain(+Geometry)` ، `Geometry → Domain(+Math)` ، `Domain → هیچ`. هیچ لایه‌ای به WPF ارجاع نمی‌دهد؛ بنابراین هستهٔ هندسی، دامنه، ماندگاری و خروجی‌ها روی لینوکس ساخته و **آزمون واقعی** می‌شوند.

## ۴. تصمیم‌های کلیدی ثبت‌شده

1. **دقت هندسی در برابر امکان‌سنجی:** پروفایل involute از روی دایرهٔ پایه با پارامتر «خطای وتر» (chordal tolerance) نمونه‌برداری می‌شود، نه با تعداد نقطهٔ ثابت؛ مقدار مؤثر در تنظیمات خروجی نمایش داده می‌شود (الزام سند ۰۴).
2. **فرمول‌های پایه:** برای چرخ‌دندهٔ استاندارد full-depth بدون اصلاح پروفیل از روابط مرجع متداول (ISO/دین طراحی ماشین) استفاده می‌شود: `d=m·z`، `da=m(z+2)`، `df=m(z−2.5)`؛ برای داخلی `da=m(z−1.6)` و `df=m(z+2.5)` (با addendum کوتاه‌شدهٔ متداول 0.8m). این‌ها «تقریبی/آزمایشی» علامت می‌خورند مگر با مرجع مستقل آزموده شوند — آزمون‌های عددی با محاسبهٔ مستقل در `tests` همین کار را می‌کنند.
3. **مارپیچ:** مدول عرضی `mt=mn/cos(β)` و زاویهٔ فشار عرضی `tan(αt)=tan(αn)/cos(β)`؛ بدنه با برش‌های موازی صفحهٔ عرضی که هر برش به‌اندازهٔ `tan(β)·z_slice` می‌چرخد ساخته می‌شود. دقت هندسی به تعداد برش وابسته است و در گزارش خروجی ذکر می‌شود.
4. **مش به‌جای B-rep:** خروجی‌های سه‌بعدی همگی **مش مثلثی** هستند و در UI صریحاً «خروجی مش» نامیده می‌شوند؛ STEP/IGES به‌دلیل نبود هستهٔ CAD با مجوز مناسب در نقشهٔ راه است و هرگز مش مثلثی به‌عنوان B-rep معرفی نمی‌شود (الزام سند ۰۴).
5. **صداقت قابلیت:** کاتالوگ قابلیت به‌صورت کد (`CapabilityCatalog`) با وضعیت واقعی هر خانواده/فرمت پیاده شده و UI فقط موارد «پیاده‌سازی‌شده» را فعال نشان می‌دهد؛ انتخاب نوع راه‌راه پیام راهنما می‌دهد، نه مدل جعلی.
6. **آفلاین و بازخورد:** ارسال بازخورد فقط با رضایت صریح و از HTTPS به سرویس سمت‌سرور انجام می‌شود؛ چون backend واقعی تنظیم نشده، دکمهٔ ارسال با وضعیت «سرویس ارسال پیکربندی نشده» غیرفعال و صادقانه اعلام می‌شود (الزام سند ۰۵).
7. **اطلاعات سازنده:** نام/تلفن/ایمیل/وب‌سایت از یک منبع تنظیم واحد (`AppInfo`) می‌آید؛ شمارهٔ کامل کارت بانکی در هیچ فایلی وجود ندارد.
8. **فونت:** Vazirmatn (مجوز OFL 1.1) به‌صورت منبع محلی در `App/Assets/Fonts` بسته‌بندی و از `Resources` بارگذاری می‌شود؛ نصب فونت در ویندوز لازم نیست. متن مجوز در `ThirdPartyNotices` قرار می‌گیرد.

## ۵. محدودیت‌ها و ریسک‌های شناخته‌شده

| مورد | توضیح صادقانه |
|---|---|
| ساخت/اجرای UI | پروژهٔ WPF فقط روی ویندوز (با `dotnet publish -r win-x64 --self-contained`) ساخته می‌شود؛ این محیط توسعه لینوکسی است، پس UI ساخت و اجرای عینی نشده و در گزارش نهایی همین گونه ثبت می‌شود. هسته به‌طور واقعی روی لینوکس build و test می‌شود. |
| رندرر پیش‌نمایش | رندرر نرم‌افزاری برای مدل‌های سبک/متوسط (تا چند صد هزار مثلث) مناسب است؛ برای مش‌های بسیار سنگین ممکن است نرخ فریم پایین بیاید. |
| فیلهٔ ریشهٔ دندانه | با کمانی محافظه‌کارانه (تا سقف نیم‌فضای موجود) مدل می‌شود؛ تنش ریشه و اثر ابزار تولید تحلیل نمی‌شود. |
| تماس/تداخل | بررسی برخورد جفت‌دنده‌ها به‌صورت تقریب مش‌بندی/فاصلهٔ اسمی است و در UI با برچسب «تقریبی» اعلام می‌شود. |
| سینماتیک | نسبت/جهت دوران ایدئال (صلب) برای زوج/قطار/سیاره‌ای محاسبه می‌شود؛ لقی، بار، راندمان و عمر مدل نمی‌شوند. |
| STEP/IGES | پیاده‌سازی نشده؛ دلیل: نیاز به هستهٔ CAD با مجوز و حجم مناسب. |

## ۶. ترتیب اجرا (برش عمودی طبق سند ۰۶)

1. ✅ مرحلهٔ ۰ — همین سند.
2. اسکلت راهکار + هستهٔ Domain (پارامتر، اعتبارسنجی، کاتالوگ).
3. برش عمودی: چرخ‌دندهٔ خارجی ساده از پارامتر تا مش.
4. ماندگاری `.sgdproj` + خروجی STL (round-trip و اعتبارسنجی).
5. خانواده‌های پایه: مارپیچ، جناغی، داخلی، رک + ویژگی‌های بدنه.
6. مونتاژ: زوج، قطار مرکب، سیاره‌ای پایه.
7. خروجی‌های بیشتر OBJ/PLY/GLB + تنظیم کیفیت.
8. UI ویندوزی کامل + فونت + بازخورد/درباره.
9. آزمون‌ها، CI، مستندات، نمونه‌ها و گزارش نهایی.
